## 구현 범위

1. **설정과 결제 권한.** 팀 전용 PG 환경/상점·허용 수단·사업자 스키마·자동결제 실패 재시도/중지·환불의 미사용분 처리·금액 반올림·명세 발행 달력을 버전 있는 명시 설정으로 검사한다. 없는 설정은 해당 판매/실행을 차단한다. 팀 소유자나 현재 결제 위임만 구매/정보/명세를 읽고 변경한다. 프로젝트 콘텐츠 접근을 결제 권한에서 파생하지 않는다.
2. **사업자 정보와 결제 수단.** 향후 주문에 적용할 프로필과 당시 주문 사본을 분리한다. 팀·PG 환경에 묶인 수단 등록/교체/삭제와 동의 기록을 구현하고 원키로 복구한다. PG 수단 식별자/마스킹만 표시하며 전체 카드/보안 코드를 서버/로그/브라우저 저장소에 저장하지 않는다. 등록 콜백만으로 빌링 키나 소유권을 신뢰하지 않는다. 서버 대조 후 확정하고 개인 빌링 키와 namespace/암호화 문맥을 분리한다.
3. **실제 S21~S23 구매 흐름.** 서버 견적→조건/공급가액·VAT·합계·한국 시간 대상 E 확인→고정 주문→PG checkout→현재 원주문 조회→수납 확인/반영 중/반영 완료로 이어간다. 첫 구매·현재 기간 추가·다음 한 달 선구매·종료 뒤 복구를 구분한다. 금액/상품/대상 기간을 URL이나 브라우저 성공에서 확정하지 않는다. 한 번만 생성된 주문/시도/수납을 기존 적용 작업자에 연결한다. 결제 권한이 회수된 뒤 응답 복귀로 새 허용을 만들지 않는다.
4. **자동갱신과 다음 기간 정원.** 자동/단건 방식 변경만으로 즉시 과금/지급하지 않는다. 이미 산 다음 기간은 조건을 유지하고 자동결제를 건너뛴다. 다음 미구매 기간의 정원/유지 대상을 영속 저장하며 미지정 부족분을 자동 구매하지 않는다. 원래 KST 기준일과 E를 유지한다. 단건 전 진행 중 자동 시도를 잠금 아래 중지/조회하고 이미 수납됐다면 같은 기간 새 주문을 만들지 않는다. 원기간/시도/고정 공급자 식별자로 장애/재시작을 대조한다. 재시도 제한/중지는 승인 설정에 따르며 개인/다른 팀 청구가 섞이지 않는다.
5. **통지와 수납 복구.** 공급자 공식 계약에 맞는 인증/서명 또는 조회 증명을 검사하고 원거래를 대조한다. 중복/역순/지연/금액 불일치/기한 후 이체/취소를 허용 상태 전이로 처리한다. 공급자 성공 뒤 DB/audit 실패·응답 유실·프로세스 종료에도 원시도를 확인하고 재청구하지 않는다. 판매 플래그 중지는 새 수납과 과거 실제 수납 조회를 구분한다. 불명/미적용 복구 수납은 기존 삭제 차단을 유지하며 단순 타임아웃으로 해제하지 않는다.
6. **원주문 환불과 정산.** 승인된 정책으로 원주문의 환불 대상 미사용분을 먼저 예약하고 공급자 원취소/대조·실제 환불 기록·제공량 조정을 연결한다. 이미 처리한 과납 채무는 중복 지급하지 않는다. 진행 중 AI 예약·회수 대기/장치 허가·저장량과 경합할 때 허용 없는 제공량/잔액을 만들지 않는다. 공급자 불명 상태를 환불 완료로 표시하지 않는다. 기존 불변 지급 건/원장/수납을 덮어쓰지 않고 정정 기록을 추가한다. 임의 전액 환불·음수 잔액·과거 기간 리셋·배정 해제 자동 환불을 만들지 않는다.
7. **S24/S25 월 명세와 PDF.** KST 달력 월의 기본/추가 이용권/AI/저장 구매 금액과 AI 지급·사용·예약·반환·만료를 단위별로 구분한다. 기존 선결제 사용량을 다시 청구 금액에 더하지 않는다. 결제 권한만으로 비공개 프로젝트명/파일명·내용을 포함하지 않는다. 다음 달 3영업일 운영 기본값의 달력과 정정 조건을 명시한다. 확정 문서는 당시 사업자/주문/원장 사본의 불변 revision/PDF·전체 해시로 보존하며 늦은 정산은 사유 있는 새 revision이다. 과거 프로필 수정으로 PDF를 바꾸지 않는다. 문서는 월 명세이며 세금계산서로 표시하지 않는다. 법정 발행/수정은 승인된 별도 설정/어댑터가 없으면 차단한다.
8. **웹 전체 복구와 화면.** 구매/결제정보/다음 기간/환불/월별 명세의 실제 서버 화면을 연결한다. 서비스·계정·팀별 원입력/원키/원주문을 변경 전 영속 저장하고 응답 유실·새로고침·PG 복귀 뒤 조회로 처리 여부를 확인한다. 계정/팀 변경과 오래된 응답에서 이전 사업자 정보/문서/checkout을 노출하지 않는다. 조회 실패를 미결제/빈 목록/성공으로 바꾸지 않는다. 결제 거절·수납 불명·미적용·운영 확인·환불 처리 중을 구분하고 프로젝트 내용에 대한 일반 우회 진입을 만들지 않는다.

## 병렬 경계와 통합

- Codex는 native 작업 파일·NAS 재연결·전송/발행·최종 통합, Claude C는 영상 검토본/검토/공유/승인, Claude D는 실제 팀 AI 견적/실행/결과와 앱/웹 S30을 맡는다. E는 새 결제/갱신/환불/명세 도메인에 집중한다. AI 실행·review·native parser·앱 library/IPC를 직접 대폭 변경하지 않는다. 이용권/AI 지급/파일 수명과 필요한 연결은 기존 accessor와 작은 integration 커밋으로 제시한다.
- 공통 `contracts.ts`, module/controller·worker 등록, schema index, migration journal, 웹 생성 계약/팀 홈 진입은 `(integration)` 표시 별도 커밋으로 나눈다. 생성 계약은 서버에서 동기화한다. 현재 서버에는 native 정책/parser와 참여 회차 0063이 포함돼 있으므로 유지한다. 정식 0000~0063 migrations를 수정/삭제하지 않는다. 자기 분기 0064 이후 번호는 C/D와 충돌할 수 있으므로 인계에 의존 순서를 적고 통합 담당이 빈 DB에서 조정한다.
- 원주문/수납/기간 적용은 같은 팀 잠금과 기존 식별자를 사용한다. 별도 팀 유료 기간이나 병렬 AI 지급 원장을 만들지 않는다. E와 D 공통 AI 지급/환불 경합은 공개 인터페이스·불변 원장과 검증 시나리오로 인계한다. 실제 팀 전체 삭제/백업/지원 콘솔은 이 배정 범위 밖이며 기존 복구 수납 차단은 보존한다.
- 미정 상품·PG·환불·세금/달력 값은 설정 누락 상태로 표현한다. 시장 조사 제안이나 기존 개인 서비스 기본값으로 정책을 확정하지 않는다. 실제 자격 증명·JWT·checkout/서명 URL·빌링 키·사업자 전체 사본을 일반 로그/스크린샷/HANDOFF에 넣지 않는다.

## 검증과 알려진 미해결

실제 PostgreSQL/Nest/JWT/엄격 DTO, 브라우저와 로컬 HTTP PG 대역으로 견적→주문→PG 결과→수납→실제 기간/정원/AI 반영→명세 PDF까지 실행한다. 실제 PG와 다른 대역 부분을 구분한다. 테스트 개수로 전체 완료를 계산하지 않는다.

- 동시 같은 키/같은 견적/마지막 주문, 성공 직후 종료·응답 유실·DB/audit 실패·중복/역순 통지, 단건/자동/선구매 경합을 검사한다. 단일 수납/단일 지급과 원시도 대조가 근거다.
- 1월 31일/2월 말일/3월 31일, E 정각·지연 적용·과납·기한 후 수납·오래된 일할/복구 주문, 판매 플래그 중지 후 기존 수납/선구매, 다음 정원 미지정/이미 구매한 기간 불변을 확인한다.
- 결제 위임 회수/멤버·계정 정지/다른 팀/개인 분리, PG 수단 등록 변조·환경 혼용·수납 금액 불일치·같은 공급자 이벤트의 다른 원주문 치환을 검사한다.
- 환불 예약/사용/AI 예약 경합, 일부 환불/중복 대조/공급자 불명/회수 대기, 만료 지급분을 새 잔액으로 부활시키지 않는 원장 조정을 확인한다.
