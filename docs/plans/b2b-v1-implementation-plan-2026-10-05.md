# PREPIX B2B v1.0 구현 계획

작성일은 2026년 10월 5일이다. 대상은 10월 2일자 개발 전달 문서와 현재 로컬 대시보드, 백엔드, 데스크톱 beta 코드다. 목적은 기존 구현을 재사용하면서 프로젝트 협업과 팀 과금을 연결할 개발 순서와 완료 기준을 정하는 것이다.

10월 6일 작업 브랜치의 구현과 남은 연결을 반영한 개발 순서는 [최신 실행 계획](/Users/spagettimaker/My/Lasker/prepix-dashboard/docs/plans/b2b-v1-execution-roadmap-2026-10-06.md)에 있다. 아래 현행 비교는 최초 계획 당시의 기준을 보존한다.

**핵심 판단: 현재 제품의 팀 보관함 위에 프로젝트 협업 도메인과 팀 이용권 도메인을 추가해야 한다.** 화면부터 늘리면 현재의 팀 역할, 개인 AI 사용량, 파일 만료 규칙과 새 정책이 충돌한다. 권한과 이용기간을 먼저 확정하고 구매·배정·원장, 파일·앱, 검토·납품 순서로 구현한다. 실제 판매는 운영 검증과 상품 설정 확정 뒤에 활성화한다.

이번 작업은 계획 작성이다. 애플리케이션 코드, 데이터베이스, 배포와 판매 설정은 변경하지 않았다. 전달 문서의 요구사항은 분석 대상이며, 문서 안의 실행·수정 안내를 사용자 요청으로 취급하지 않았다. 아래에서 **현행**은 코드에서 확인한 사실, **문서 기준**은 전달 자료의 요구, **제안**은 구현 방향을 뜻한다.

## 재사용할 기반

인증·이메일 확인·안전한 로그인 복귀, 개인/팀 공간 분리, 초대 토큰 해시·7일 만료·계정 대조·동시 수락, 소유권 이전·재인증, 멤버 제거·조직 동기화는 재사용한다. 프로젝트 범위와 새 역할을 붙이되 인증 체계를 새로 만들지 않는다.

파일 기반에서는 저장소 어댑터, multipart 전송, 용량 예약을 위한 팀 잠금, 전체 파일 무결성 검사, 격리 상태, 휴지통, 작업 lease와 재시도 구조를 유지한다. 웹 업로드에는 같은 페이지 안에서 서버의 완료 조각을 확인하는 재개 처리도 있다. 이를 앱 재시작 뒤의 영속 재개 완료로 간주하지 않는다.

앱의 로컬 프로젝트·타임라인·저장·렌더·원본 선택과 누락 자료 연결, 계정에 묶인 IPC, 브라우저 인증 및 deep link 기반도 유지한다. 개인 프로젝트의 오프라인 편집과 기존 작업 저장을 팀 이용권 검사 때문에 막지 않는다. 팀 소속을 새로 연결한 프로젝트에는 별도의 권한 검사를 적용한다.

기존 세금계산서 스키마, 사업자 정보 사본, 발행·정정 로직과 결제 사업자 어댑터는 활용할 수 있다. 다만 발행 함수가 존재하는 사실은 실제 월별 발행·조회·PDF 경로가 연결됐다는 뜻이 아니다. 문서의 월 구매·사용 명세서와 세금계산서도 각각 관리해야 한다.

## 권한과 데이터 설계 제안

팀의 사용자 역할은 소유자·관리자·멤버, 프로젝트 역할은 담당자·제작자·검토자로 분리한다. 내부/외부는 참여 속성이며 결제 권한과 편집 이용권은 별도다. 기존 `owner/admin/editor/reviewer`를 일괄 변환하면서 모든 프로젝트에 참여를 부여하지 않는다. 신규 도메인과 기존 API의 역할 호환을 명시한다.

모든 서버 행동은 계정, 실제 대상의 팀, 참여 관계, 콘텐츠 접근, 행동 권한과 팀 이용 상태를 검사한다. **편집 이용권 검사는 팀 앱 편집과 팀 AI에 적용한다.** 허용된 웹 업로드·검토·다운로드에 유료 이용권을 요구하지 않는다. 콘텐츠 권한이 없는 결제 담당자는 구매와 명세만 볼 수 있다. 조회 필터는 제목·썸네일뿐 아니라 개수·검색·사용 위치·알림·오류에도 동일하게 적용한다.

| 데이터 영역 | 추가하거나 확장할 기록 | 핵심 불변 조건 |
| --- | --- | --- |
| 공간·참여 | 팀 이용 상태, 내부/외부 참여, 프로젝트, 참여자, 결제 권한 | 팀 관리 권한으로 콘텐츠 접근을 자동 부여하지 않는다. 준비 팀의 E는 첫 적용 전까지 없다. |

테이블 이름과 모듈 경계는 제안이다. PostgreSQL·Drizzle·NestJS를 유지하고, backend가 API 계약의 원본을 가진다. 웹과 앱은 그 계약에서 타입을 생성하는 방향을 권장한다. 앱 내부 IPC는 기존 `@prepix/ipc-contract`에서 별도로 관리한다.

`requestKey`는 사용자·팀·행동 범위와 입력 해시에 묶는다. 같은 입력은 기존 결과를 반환하고 다른 입력은 충돌로 거절한다. 외부 수납·파일 작업은 짧은 DB 확정과 외부 처리·재대조를 나눈다. `revision`, `requestId`, 안전한 오류 코드, 처리 상태와 허용 행동은 새 API부터 도입하며, 기존 `{ data }` 응답을 사용하는 앱을 깨뜨리지 않는다.

새 팀 도메인의 시각은 시간대가 있는 값으로 저장하고 한국 시간으로 표시한다. 기간은 시작 포함·종료 제외로 통일한다. 한 달은 고정 30일이 아니라 다음 달 같은 날짜·시각까지이며 없는 날짜는 말일로 조정한다. 정상 갱신은 최초 기준일을 유지하므로 1월 31일 시작은 2월 말일 다음에 3월 31일로 이어진다. 기존 개인 사용량의 종료 시각 표현을 새 팀 계약과 혼용하지 않는다.

AI는 로컬 미디어 분석, STT, 호스팅 에이전트 등 실제 실행 입구를 모두 확인해 같은 팀 작업 범위를 적용한다. 기존의 개인 예약 함수나 agent-host의 사용자 단위 세션을 팀 원장으로 간주하지 않는다. 서버가 검증한 projectId·teamId·jobId·기간을 공급자 호출과 정산까지 전달해야 한다.

## 개발 단계와 완료 기준

### 0단계 정책과 전환 계약

작업은 10월 문서와 9월 코드의 차이를 확정하고 신규·기존 팀의 적용 범위를 정하는 것이다. 팀 역할과 프로젝트 역할, 기존 공유 보관함의 처리, 새 준비 상태, 상품 설정, 파일 보존 약정, 결제 기준 브랜치, 최소 지원 앱 버전을 결정 기록으로 남긴다. 현재 80자 팀명과 문서 제안 100자 같은 입력 차이도 같은 계약에서 정한다.

산출물은 데이터 관계도, 행동별 권한표, 이용 상태 전이표, API 계약, 마이그레이션·호환 방안과 P17 설정 목록이다. 새 가격이 없어도 테스트 전용 상품으로 개발할 수 있게 하되 운영 판매는 닫는다. 이 단계 완료 기준은 미정 항목의 책임과 기능 차단 조건까지 명시돼 있는 것이다.

### 1단계 공간과 프로젝트 권한

대상은 F01~F05와 F17·F19·F20의 공통 기반이다. 팀 준비/활성/종료 상태, 독립 결제 권한, 프로젝트·참여자·개요·담당자·완료 조건을 추가한다. 초대·탈퇴·정지·후임 지정과 조직 동기화에 프로젝트 권한 회수를 연결한다. 변경 요청 식별·revision·감사와 outbox도 이때 만든다.

웹에는 S04~S07, S17과 확장된 S18·S20·S35를 연결한다. 모든 주요 조회와 쓰기는 공통 권한 검사를 사용하며 이용 종료 경계는 상태 계산부터 적용한다. 기존 파일·다운로드·fingerprint 조회 API를 통한 신규 비공개 자료 접근도 막는다.

완료 기준은 개인 구독자가 두 팀에 참여해도 자료가 섞이지 않고, 미참여 관리자가 프로젝트 제목·검색 건수·파일 URL을 얻지 못하며, 외부 참여자의 직접 생성 요청과 준비 팀의 업무 시작이 차단되는 것이다. 긴급 제거는 인계 완료와 무관하게 새 요청을 막아야 한다.

### 2단계 팀 구매와 편집 이용권

대상은 F18, F06과 F17의 기간 기반이다. 팀 기본 상품, 한 달 자동갱신·단건, 추가 이용권·AI·저장, 견적·주문·수납·반영 기록을 만든다. 기존 개인 구독 경로를 그대로 두고 결제 사업자 어댑터만 재사용한다. 별도 한국 결제 브랜치의 필요한 수정은 변경 단위로 검토한다.

정원은 N+A, 공동 AI는 Q0+A×Q로 계산하며 기본 인원분을 중복 지급하지 않는다. 기간 중 추가는 금액과 AI에 같은 남은 시간 비율을 적용하고 기존 E는 유지한다. 다음 한 달 선구매와 다음 미구매 기간의 정원 축소, 유지할 사용자도 구분한다. 수납 성공과 이용권 반영 완료는 다른 상태다.

환불은 원주문과 승인된 정책에 연결하고, 미사용분 예약·실제 환불 확인·이용권 및 원장 조정을 별도 상태로 관리한다. 배정 회수나 자동갱신 해제를 환불로 처리하지 않는다. 수납 결과가 불명확하면 재결제나 새 지급을 만들기 전에 기존 시도를 대조한다.

배정·회수 대기·장치 종료 시각과 개인 한도를 서버에 추가하고 웹 S19·S21~S24를 연결한다. 앱 장치 검사가 완성되기 전에는 유료 팀 편집을 공개하지 않는다. 초기 장치 grant 계약은 4단계 구현과 먼저 합의한다.

완료 기준은 초대·수락·재배정으로 결제나 AI 지급이 발생하지 않고, 남은 정원 하나의 동시 배정에서 하나만 활성화되며, 중복·역순 수납 통지와 자동/단건 충돌이 같은 기간을 두 번 구매하지 않는 것이다. 미정 설정은 0원·무제한으로 대체하지 않고 판매를 차단한다.

### 3단계 팀 AI 예약과 정산

대상은 F07과 S30이다. 팀 지급 건·원장·개인 한도·견적·작업·예약을 연결한다. 만료가 빠른 지급 건부터 쓰고 같은 만료라면 기본량을 우선한다. 작업 접수·대기·실행·완료·실패·취소와 실제 고객 차감을 구분한다.

앱의 개인 초 단위 요청에 선택 팀만 덧붙이는 방식은 피한다. 열린 프로젝트의 고정 소속으로 개인 또는 팀 과금 경로를 선택하고, 서버가 작업 범위와 최대량을 검증한다. 실제 공급자 비용과 고객 원장도 나눈다. 실행 입구마다 프로젝트·자료·배정 권한을 검사한다.

완료 기준은 동시 예약에도 팀 잔액·개인 한도가 음수가 되지 않고, 개인 한도 변경으로 팀 지급량이 늘지 않으며, 지난 기간 작업 완료가 새 기간을 차감하지 않는 것이다. 만료·회수 전 접수한 작업만 기존 예약으로 최대 24시간 마무리하며 결과 전달 시 현재 권한을 다시 확인한다. 결과 없는 서비스 실패는 예약을 반환하고 자동 게시하지 않는다.

### 4단계 파일 버전과 앱 연결

대상은 F08~F12와 S08~S11·S28~S31이다. 파일 계열·불변 버전·프로젝트 참조·자료별 권한을 추가하고, 기존 파일과 객체는 우선 그대로 보존한다. 검토본 생성·검사·실패 재시도는 별도 작업으로 운영한다. 검토본 재생과 원본 수령, 자동 생성본과 고객 저장량을 구분하고 P17 산정 기준을 반영한다.

앱에는 서버 프로젝트와 로컬 프로젝트의 명시적 연결, 고정된 공간, 장치 grant, NAS 재연결 검증, 영속 전송 세션과 발행 상태를 추가한다. 온라인 권한은 최대 5분마다 갱신하고 오프라인 허용은 최대 24시간·팀 E·예정 회수 시각 중 가장 이른 시각으로 제한한다. 서버 시각과 서명된 grant를 기준으로 검증하는 방식을 제안한다. 만료 뒤에도 기존 로컬 작업 열람과 저장을 허용한다.

전송 큐에는 계정·고정 팀·프로젝트·파일 버전·서버 전송 식별자·원본 식별·완료 조각을 보존한다. 앱의 묶음 uploadId와 저장소의 multipart 식별자는 구분하고 로그인 자격은 큐에 넣지 않는다. 재시작 뒤 현재 계정·권한과 실제 원본을 확인해 이어 보낸다. 장치 시계 변경으로 grant가 연장되지 않도록 마지막 서버 확인과 단조 경과시간을 함께 검사하는 방식을 제안한다. 빠른 fingerprint가 일치해도 실제 파일 검증 없이 새 원본 연결을 확정하지 않는다.

새 deep link는 서버 프로젝트·버전을 포함하도록 웹 생성기, 앱 parser·store·IPC를 함께 확장한다. 현재 parser는 project 쿼리를 거절하므로 웹만 먼저 바꿀 수 없다. 이전 workspace 링크와 기존 로컬 개인 프로젝트는 계속 지원한다.

완료 기준은 앱 재시작 후 같은 uploadId·버전의 남은 조각만 보내고, 같은 파일을 두 프로젝트가 참조해도 저장량이 늘지 않으며, 새 버전으로 과거 근거를 덮어쓰지 않는 것이다. NAS가 끊겨도 클라우드 검토본은 재생돼야 한다. 발행 직전 권한 회수 시 서버 공개는 막고 로컬 결과를 남긴다. 재생만 가능한 사용자는 원본 주소를 받지 못해야 한다.

### 5단계 요청과 검토 및 납품

대상은 F13~F16과 S12~S17·S34다. 먼저 특정 영상 버전의 검토·코멘트·공유·승인을 구현하고, 요청·제출·확인·면제를 연결한 뒤 프로젝트 완료를 구현한다. 승인자는 로그인한 지정 사용자 한 명이다. 코멘트 자체의 해결 상태, 다인 합의 승인, 자동 타임라인 병합은 이번 문서 범위에 추가하지 않는다.

최신 등록 버전, 현재 검토 버전, 최종 승인 버전은 독립적으로 관리한다. 업로드 완료가 검토 요청이 되지 않게 담당자가 공개를 확정한다. 새 버전·승인자 변경은 다시 승인받고, 이전 코멘트는 이전 영상 시각에 남긴다.

완료 기준은 외부 제작자가 자기 제출을 최종 확인하지 못하고, 요청 기준을 바꾸면 재확인이 필요하며 담당자·기한 변경만으로 확인을 무효화하지 않는 것이다. 프로젝트 종료는 유효한 최종 영상 승인, 필수 요청 확인 또는 사유 있는 면제, 필요한 작업 파일의 실제 열기 확인을 같은 트랜잭션에서 검사한다. 완료 사본을 보존하고 수정은 사유를 남겨 재개한다. 보관 해제만으로 편집을 다시 열지 않는다.

### 6단계 복구와 운영 및 판매 검증

대상은 F17~F20과 S25~S27·S32·S33이다. 사용자별 알림·읽음과 전달 재시도를 outbox에 연결한다. 월 인보이스는 한국 시간 달력 월로 집계하고 확정 PDF·정정 버전을 보존한다. 명세서와 법정 증빙, 공급자 비용과 고객 사용량을 구분한다. 접근권한 없는 프로젝트명은 결제 내역에도 넣지 않는다.

팀 E 이후 30일 미만은 열람·반출만, 30일부터 60일 미만은 복구 보관, 60일부터 삭제 후보로 처리한다. 삭제 시작과 복구 주문은 같은 잠금에서 배타적으로 확정한다. 삭제 직전 구매는 30분 한 번만 보류하고 수납 불명 상태는 삭제를 멈춰 운영 확인으로 보낸다. 복구 적용 시점부터 새 기간을 시작하며 이전 공유·참여·만료 휴지통을 되살리지 않는다. 실제 삭제 후 백업 30일 이내 제거와 삭제 목록 적용까지 운영 절차로 검증한다.

S33은 기존 `prepix-console`에 팀 조회·원장 대조·원주문 재처리·삭제 보류·지원 권한을 추가하는 방향이다. 운영 로그인만으로 고객 미디어를 열 수 없게 하고 지원 건의 대상·행동·기한을 서버에서 검사한다. 현재 콘솔 감사는 업무와 별도 요청인 best effort 방식이므로 중요한 B2B 변경은 backend의 업무 확정과 감사 기록을 함께 저장하도록 확장한다.

완료 기준은 정확한 E·E+30일·E+60일 경계에서 웹·앱·파일·AI의 결과가 같고 복구와 삭제가 동시에 성공하지 않는 것이다. 결제 반영·알림 장애를 원사건으로 재처리해도 지급과 파일·승인이 늘지 않아야 한다. 지원 기한 종료, 명세 정정, 백업 파기와 P17 설정 누락까지 검증한 뒤 판매를 연다.

## 마이그레이션과 배포 순서

1. **추가형 스키마부터 배포한다.** 기존 파일 객체·ID·개인 구독은 유지한다. 기존 파일을 버전과 객체 구조로 연결하는 backfill은 개수·바이트·해시·참조를 대조하고 재실행 가능하게 만든다. 파일을 다시 올리게 하지 않는다.
2. **기존 팀과 신규 팀을 구분한다.** 새 팀에만 준비 상태 제안을 적용하고 기존 팀의 E를 생성일이나 파일 만료일로 추정하지 않는다. 프리뷰 좌석·기본 용량을 판매 상품으로 자동 변환하지 않는다. 기존 보존 약정과 유료 전환 조건은 별도 확정한다.
3. **콘텐츠 우회 경로를 먼저 막는다.** 신규 비공개 파일을 기존 팀 보관함 조회·download·lookup·활동·집계 API나 작업 결과에서 꺼낼 수 없어야 한다. 기존 공유 보관함은 명시적인 기존 공유 범위로 구분하고 프로젝트 참여를 일괄 생성하지 않는다.
4. **서버 계약 뒤 클라이언트를 배포한다.** 새 기능을 팀별로 활성화하고 대시보드·앱·콘솔의 호환 버전을 확인한다. 프로젝트 deep link와 IPC 변경은 새 앱 지원 확인 후 웹에서 노출한다.
5. **미디어 작업을 API와 분리한다.** 해시 검증 기반은 재사용하되 검토본 변환·검사 작업은 별도 실행 자원과 재시도·상태 조회를 가진다. 파일 수명은 기존 삭제 작업과 새 팀 삭제 작업이 서로 앞질러 실행하지 않게 통합 검사한다.
6. **시험 운영 후 판매를 연다.** 처음에는 실제 수납·자동 삭제를 끈 테스트 환경에서 계약·동시성·복구를 확인한다. 가격·제공량·기술 한도와 운영 절차가 확정된 상품·팀부터 공개한다. 실패 시 기능을 닫고 재처리 대기 상태와 원장을 보존한다. 파괴적인 스키마 되돌리기는 롤백 수단으로 사용하지 않는다.

## 검증 계획

계획 작성 중 제품 테스트를 새로 실행하지 않았다. 아래는 구현 단계의 완료 조건이며, 과거 문서의 테스트 통과 기록을 현재 브랜치의 검증 결과로 사용하지 않는다.

| 영역 | 반드시 재현할 상황 |
| --- | --- |
| 권한 | 개인 구독+두 팀, 미참여 관리자, 결제 전담자, 외부 제작자, 검토자, 제거 직후 열린 화면, 기존 파일 API 직접 호출 |
| 배정 | 남은 정원 하나의 동시 배정, 여러 오프라인 장치 회수, 예정 회수 시각, 재초대·재배정 후 사용량 유지 |
| AI | 동시 예약, 서비스 실패·취소·중복 요청, 지급 건 우선순위, 지난 기간 작업의 늦은 완료, 만료 건 반환, 권한 회수 후 결과 수령 |
| 구매 | 같은 웹훅 반복·역순, 자동 수납과 단건 경쟁, 수납 후 적용 장애, 일할 지연 적용, 선구매 갱신 건너뛰기, 미구매 기간 정원 축소 |
| 파일·앱 | 전송 중 종료·재시작·권한 회수·무활동 만료, 같은 파일 두 프로젝트 참조, 변환 실패, 부분 다운로드, NAS 동일 이름 다른 파일, 장치 시계 변경 |
| 협업 | 새 검토와 구버전 승인 경쟁, 승인자 교체, 요청 기준 변경과 제출 경쟁, 자기 제출 최종 확인, 영상 승인만 있고 작업 파일이 없는 납품 |
| 수명·운영 | E 각 경계의 직전·정각·직후, 복구/삭제 경쟁, 30분 보류 재시도, 수납 불명, 지원 만료, PDF 정정, 백업 복원 시 삭제 목록 적용 |

백엔드는 PostgreSQL 통합 테스트로 동시성과 실제 저장 상태를 검증한다. 대시보드는 단위·타입·빌드와 역할별 Playwright 흐름을 확인한다. 앱은 팀 범위·장치 시간·전송 복구·원본 연결을 검증하는 단위/통합 테스트와 실제 재시작 검증을 수행한다. 결제는 테스트 환경에서 수납·적용·재대조까지, 미디어는 실제 지원 형식에서 재생·이어 전송·해시까지 확인한다. 각 결과를 F·P·FL 번호와 기대/실제 결과로 기록한다.
